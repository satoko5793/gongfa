# 功法项目重构 Roadmap

## 目标

这一轮重构的目标，不是重写项目，也不是切技术栈，而是把 `gongfa` 从“功能能跑但维护成本高的单体项目”，优化成“边界清楚、规则可解释、后续好改的单体项目”。

当前优先级最高的真实痛点不是 UI，而是下面几件事：

- 调价配置保存后，现货是否真的同步重算，不够透明
- 双满、词条、老卡、双词条、金卡专属规则互相叠加后，很难快速解释
- 重算入口散在多个位置，出问题时经常要人工 SSH 查数据
- 后台能改价格，但对“为什么是这个价”的解释仍然偏弱

## 对比参考

这次路线主要参考两个项目：

### `sida-mvp`

值得借鉴的点：

- 前后端边界更清楚
- 后端天然分成 `interfaces / services / workflows / models / tests`
- 测试目录完整，单元测试和集成测试是第一方能力
- 前端按 `pages / services` 收口，而不是长期堆大文件

### `claude-code`

值得借鉴的点：

- 按能力分目录，而不是按“历史文件”堆积
- 规则和注册点更集中，新增能力时有固定落点
- 状态、运行时、工具调用边界更清楚
- 扩展点先设计，不等业务长歪后再补

## 当前项目结构问题

`gongfa` 目前已经有业务闭环，问题主要是结构治理落后于业务增长。

当前最明显的问题：

- `backend/src/services/pricing.js` 过大，规则、解释、重算、市场因子全挤在一起
- `backend/src/services/dev-store.js` 同时承担文件存储、业务编排、审计、重算触发
- `frontend/admin.js` 和 `frontend/styles.css` 长期承载过多后台能力
- 价格规则和后台解释模型没有统一收口
- 价格系统第一方测试不足，回归主要靠人工验证

## 重构原则

这次路线固定遵守下面几条：

1. 保持单体，不拆微服务。
2. 保持当前 Express + 静态页方案，不引入新的前端框架。
3. 先拆最痛的子系统，不做“大而全”重写。
4. 文档先行，再做代码，再上测试服验证。
5. 正式服只收稳定版，重构类改动先在测试服跑通。

## 分阶段路线

### Phase 1：价格系统先拆

第一期只围绕价格系统收口，目标是：

- 建立 `backend/src/domain/pricing/` 稳定骨架
- 把 `pricing.js` 中最核心的纯规则和解释逻辑拆出去
- 让配置更新后的同步重算入口固定下来
- 给 `pricing_meta` 增加统一解释结构
- 后台最小展示“为什么这张卡是这个价”

### Phase 2：`dev-store` 与 repository adapter 收口

重点目标：

- 把文件存储中的商品、订单、用户、充值配置分层
- 降低 `dev-store.js` 作为“超大总入口”的耦合
- 明确 file / pg 两套 repository 的职责边界

### Phase 3：后台前端拆分

重点目标：

- 把 `frontend/admin.js` 按后台能力拆分
- 把 `frontend/styles.css` 拆成基础样式、后台样式和组件样式
- 把“充值配置 / 定价调控 / 商品管理 / 订单处理”从一个大脚本中分离

### Phase 4：统一枚举、错误信封、日志、测试脚本和发布前检查

重点目标：

- 常量和枚举单一来源
- 错误返回结构统一
- 写操作、重算操作、配置更新日志更清楚
- 发版前检查脚本补强

## 第一批实施范围

第一批只做下面这些：

- 后端定价规则核心
- 重算触发链路
- 定价配置到重算的联动
- 后台价格解释信息
- 对应的最小本地验证和测试服验证

第一批明确不做：

- 不拆 `dev-store` 全部能力
- 不系统重写 `admin.js`
- 不处理小程序目录归档
- 不引入新的前端框架或构建系统
- 不重构订单、导入、商城渲染等其他子系统

## 第一批代码落点

第一批代码范围固定为：

- `backend/src/services/pricing.js`
- `backend/src/domain/pricing/**`
- `backend/src/modules/admin/recharge-config/**`
- `backend/src/modules/admin/pricing/**`
- `backend/src/services/dev-store.js` 中与同步重算直接相关的最小片段
- `frontend/admin.js` 中价格解释展示的最小片段

## 执行节奏

每一期都遵守同一节奏：

1. 先写文档
2. 本地改
3. 本地验证
4. 只发测试服验证
5. 测试服稳定后再考虑正式服

## 当前阶段的完成标准

第一期至少达到这些标准，才算进入下一期：

- 严格双满参考价在所有档位都真实生效
- 同档位同数值下，带词条最终价不低于无词条
- 配置保存后，现货价格一定完成同步重算
- 任意一张商品都能从 `pricing_meta` 读出关键定价依据
- 商城、个人后台、后台保存配置和下单主流程不被破坏

## 不做事项

这次路线里明确不做：

- 不切换数据库方案
- 不引入 TypeScript
- 不把前端改造成 SPA 框架项目
- 不为了“重构漂亮”去打断当前业务闭环
- 不在正式服直接试验结构性改动
